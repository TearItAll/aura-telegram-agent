# 規劃任務：指定 ID 的預覽與確認

本文說明「規劃任務」如何讓 AI 產生的子任務計畫，只在使用者明確確認後才寫入，而且重複確認、同時確認或資料已變更時都不會誤寫。程式位於 `src/task-plan-actions.js`，資料表位於 `migrations/0001_task_plan_actions.sql` 與 `0003_task_plan_status_final.sql`。

## 使用者看到的流程

輸入「規劃任務：主任務名稱」後，AURA 先產生子任務預覽，**不寫入任何子任務**。預覽附上兩行可複製的指令：

```text
確認計畫 <計畫ID>
取消計畫 <計畫ID>
```

- 每份預覽都有自己的 ID。同時有 A、B 兩份預覽時，確認 A 只會套用 A。
- 預覽 10 分鐘內有效。主任務被修改、已完成、已經有子任務、預覽被取消或過期時，都會拒絕儲存。
- 同一個 ID 重複確認，回覆「已處理」，不會重複建立子任務。兩份預覽競爭同一個沒有子任務的主任務時，最多只有一份成功。
- 取消只作用於指定的 ID，也不能撤銷已經儲存的計畫。
- 只傳「確認計畫」或「取消計畫」而不帶 ID，只會顯示格式提示。

計畫 ID 是程式產生的 UUID，不是授權憑證。確認時仍要通過 webhook secret、授權使用者、私人對話與預覽擁有者的檢查。

## 預覽的內容與保護

預覽由程式組成，不由模型決定。內容包括：schema 版本、固定的動作類型、擁有者、目標任務 ID、AI 開始產生前的主任務快照，以及步驟清單。Gemini 只提供經過驗證的步驟文字（1–10 個，每個最多 150 字元），不能提供 SQL、網址或函式名稱。

- 預覽以固定欄位順序的 JSON 保存，並記錄 SHA-256 雜湊；載入時重算雜湊並核對正規化後的內容。
- 資料庫 trigger 禁止修改預覽內容欄位，並限制狀態只能從 `pending` 改一次（改成 `succeeded`、`cancelled` 或 `expired`）。
- 這些機制用來偵測意外損壞或錯誤寫入；能修改資料表結構、又能重算雜湊的資料庫管理者，不在防護範圍內。

主任務快照包括標題、狀態、優先順序、截止時間與 `updated_at`，產生預覽和確認時都會核對。這是欄位快照，不是單調遞增的版本號，所以不需要修改既有的 `tasks` 資料表。

## 確認時的交易

確認在**同一個 D1 batch** 內依序執行，D1 batch 是單一交易：

1. **SQL guard**：核對擁有者、指定 ID、狀態為 `pending`、預覽原文與雜湊、以資料庫時間判斷的有效期限、主任務快照，以及目標任務還沒有子任務。
2. 建立預覽中的所有子任務。
3. 把預覽狀態改成 `succeeded`，留下回執。

guard 在條件不符時，會刻意執行一個會失敗的 SQLite JSON 運算式，讓整批交易回復。任何一步失敗，整批都不會寫入。防止重複寫入靠的是交易內的檢查，不是交易外先 `COUNT` 再 `INSERT`。

時間只以資料庫時鐘為準：建立時間、有效期限，以及確認時的期限檢查，都用同一個資料庫時間運算式，避免 Worker 和資料庫的時鐘不一致而誤判。

## 失敗與重試

- **回應遺失**：batch 的回應不明時，重新讀取預覽狀態。看到 `succeeded` 才回報已儲存，並說明「本次沒有重複新增」；否則不回報成功。
- **已提交但回應欄位不完整**：D1 回報每個語句都成功時，就視為這次的儲存，因為 guard 在同一個交易內要求 `pending`。
- **說明失敗原因**：確認被拒絕時，會再用一筆唯讀查詢判斷原因，見 [CONFIRM-REASON-CODES.md](CONFIRM-REASON-CODES.md)。
- 重試一律使用同一個 ID，不會換新 ID，也不會改走舊的寫入路徑。

## 資料保留

預覽保存計畫文字與主任務快照，屬於個人資料。每次建立新預覽時，會順手刪除「有效期限已過至少 24 小時」的紀錄；已刪除的 ID 只會回覆找不到。這是順手清理：沒有新預覽時，資料會保留更久。

## 界線

- 不保證跨服務的 exactly-once。Telegram 重送的處理見 [TELEGRAM-DEDUPE.md](TELEGRAM-DEDUPE.md)。
- 行事曆與記憶的確認不在這套機制內。
- 主任務快照是欄位比對，同一秒內 A→B→A 的變動偵測不到（ABA）。
