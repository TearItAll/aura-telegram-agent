# AI 修改計畫：指定 ID 的預覽與確認

本文說明「AI 修改計畫」如何讓 AI 對既有計畫提出的修改，只在使用者明確確認、而且計畫從預覽到確認之間沒有被改過時，才一次套用。程式位於 `src/task-plan-revisions.js`，資料表位於 `migrations/0002_task_plan_revisions.sql` 與 `0003_task_plan_status_final.sql`。

## 使用者看到的流程

`AI 修改計畫：主任務名稱` 會請 AI 提出最多三項修改（改名或新增），並回覆預覽與兩行可複製的指令：

```text
確認修改計畫 <修改ID>
取消修改計畫 <修改ID>
```

- 每份預覽都有自己的 ID；確認 A 不會套用最後一份 B。
- 預覽 10 分鐘內有效。
- **只允許**修改「尚未開始」步驟的標題，以及在計畫最後新增步驟。不改狀態、不刪除、不重新排序，進行中或已完成的步驟不會被動到。
- 既有步驟必須是 1–10 個且編號唯一，修改後總數最多 10 個。超出範圍時不建立預覽，不會把截斷的計畫當成完整快照。
- AI 判斷不需要修改時，不建立預覽，也不影響其他仍有效的預覽。
- 取消可以重送；已成功的修改不能用取消撤銷。同一個 ID 再次確認，只回傳原本的回執，不會再改名或新增。

## 預覽的內容

預覽由程式組成，包括：擁有者、固定的動作類型、目標任務、主任務快照、**全部步驟的快照**，以及正規化後的修改內容。模型只提供步驟編號與新標題，不接受模型給的 SQL、網址、預覽 ID 或授權。

和規劃任務一樣，預覽以正規化 JSON 與 SHA-256 雜湊保存，資料庫 trigger 禁止修改內容欄位，狀態只能從 `pending` 改一次。

## 確認時的交易

在**同一個 D1 batch** 內依序完成：

1. 核對擁有者、指定 ID、狀態為 `pending`、預覽原文與雜湊，以及以資料庫時間判斷的有效期限。
2. 核對主任務的標題、狀態、優先順序、截止時間與 `updated_at`，以及步驟數量和每個步驟的 ID、編號、標題、狀態與 `updated_at`。
3. 只修改允許的「尚未開始」步驟標題、在最後新增步驟，再把預覽狀態改成 `succeeded`，留下回執。

條件不符時，guard 會刻意讓整批交易失敗；任一寫入或回執失敗，整批一起回復。多個確認或互相競爭的修改，最多一份能符合原本的快照。

## 失敗與重試

- 回應遺失時，用同一個 ID 重新讀取回執；沒有成功紀錄就不回報完成。
- 確認被拒絕時會說明原因，見 [CONFIRM-REASON-CODES.md](CONFIRM-REASON-CODES.md)。

## 資料保留與界線

- 建立新預覽時，會順手刪除過期超過 24 小時的修改紀錄；沒有新預覽時不保證會清理。
- 快照是欄位比對，不是單調遞增的版本號；資料被改動後又完整改回原樣（ABA）時偵測不到。
- 步驟備註不會提供給模型，也不會被這個動作修改。
- 不同擁有者、未來的時間戳、過期、已取消、錯誤的動作類型、預覽損壞、主任務已完成或已取消、步驟已變動，都會拒絕執行。
